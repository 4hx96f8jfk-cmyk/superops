The Problem

重复下单、重复发信、重复扣款——2026 年最大的 agent 事故区

checkpoint 让 agent「记住」，但记住不等于证明。状态快照回答不了「这条命令到底跑没跑过」。

1/4

约四分之一的工具调用可能重复

从业者实测：繁忙 agent 上约每 4 次工具调用就有 1 次可能重复。重试风暴一来，重复副作用成倍放大。

≠

记住 ≠ 执行过

行业共识：checkpoint 存的是状态，不是执行证据。它不能证明哪条命令跑过、哪封邮件发过、重试会不会重复扣款。

空档

现有方案都没站在这个位置

Temporal / Restate / DBOS 是基础设施层，得换运行时；LangGraph checkpoint 只存状态。语义层效果对账 + 不要求换框架，没人做。

Components

三个组件，一条红线

不抢编排，只治理副作用。poller / 适配器形态，pip 装上就用，agent 框架任选。

effect-ledger

效果账本

副作用的记账系统。

  • 副作用登记 + 幂等键
  • 租约 fencing，防并发重复执行
  • UNCERTAIN → 外部真值对账 → CONFIRMED / 转人工
  • 全程审计事件，事后可回放
modelhub

模型接入管理

本地 + 云端大模型的统一入口。

  • provider 注册表（OpenAI 兼容本地端点 + 云端 API）
  • 健康探活走真实推理实测——自报绿 ≠ 实际绿
  • 本地优先路由 + 回退链 + 并发闸
  • 密钥只存引用，永不入库明文；用量统计
ops-console

运维控制台

账本的可视化界面。

  • 效果账本可视化 + DAG 视图
  • 鉴权
  • 红线：只读 + 白名单命令，绝不建第二调度器
Positioning

和现有方案摆在一起看

SuperOps Temporal / Restate / DBOS LangGraph checkpoint
层次 语义层效果对账 基础设施层持久执行引擎 框架内状态快照
必须换框架 / 运行时 否（pip 装上就用） 是（负载须迁入其运行时） 是（LangGraph 体系内）
能证明命令跑过 / 邮件发过 能（效果账本 + 真值对账） 仅其运行时内部 不能（只存状态）
结果不确定时 UNCERTAIN → 对账 → 确认 / 转人工 按自身重试语义处理 无此概念
与你的编排共存 不抢编排，只治理副作用 接管执行 绑定框架
