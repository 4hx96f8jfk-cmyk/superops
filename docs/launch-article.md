# 你的 agent 可能已经下了两次单——只是你不知道

> HongYun 超级運維智能體（HongYun SuperOps）：给 AI agent 一本「到底执行过没有」的账本。今天开源。

## 一

先说一个大多数 agent 系统都躲不掉的场景。

你的 agent 调用了一个「下单」工具。请求发出去了，然后网络抖了一下，或者进程被 OOM 杀了，或者 LLM 在重试循环里又发起了一次看起来一模一样的调用。现在问题来了：**这一单，到底下没下过？**

你没法回答。agent 也没法回答。它的 checkpoint 里写着「我打算下单」，也许还写着「我下单了」——但那只是它自己的笔记。笔记不是回执。订单系统那边真实发生了什么，没人知道。于是最诚实的做法是不敢重试，或者更糟：闭着眼睛重试。

这不是假想的边角料。从业者的实测数据是：一个繁忙的 agent，大约每四次工具调用就有一次可能重复。四分之一的重复率，乘上「下单、发信、扣款、删库」这类不可逆副作用，就是 2026 年事故报告里出现频率最高的那几类名字：重复下单、重复发信、重复扣款。

行业对这件事其实有共识：**checkpoint 只能让 agent「记住」，不能证明命令跑过、邮件发过、重试会不会重复扣款。** 记忆和执行证据是两回事。但共识归共识，位置一直空着。

## 二

为什么空着？因为现有的玩家都不在这个层。

Temporal、Restate、DBOS 这一类做的是基础设施层的持久执行（durable execution）。它们很强，但前提是把你的一部分工作负载搬进它们的运行时引擎——先换框架，再谈可靠性。对已经在跑 LangGraph、CrewAI、或者干脆是裸 function-calling 的团队来说，这个迁移成本本身就是拦路虎。

LangGraph 的 checkpoint 呢？它存的是状态。状态快照回答「我走到哪一步了」，回答不了「那一步在外面世界造成了什么效果」。

于是空档很清楚：**在语义层做效果对账，同时不要求你换掉任何框架。** 这个位置没人站。

我们站过来了。思路不复杂，但要把工程做扎实：

**第一，副作用要登记，不能裸奔。** 每一次有副作用的工具调用——发邮件、写数据库、调支付接口——先在一本账上登记：这是什么操作、幂等键是什么、什么时候开始的。

**第二，不确定就承认不确定。** 调用发出后进程崩了，重启后这笔账目的状态是 `UNCERTAIN`，而不是假装成功或假装失败。这是整个设计里最重要的一条诚实原则。

**第三，拿外部真值对账。** `UNCERTAIN` 的效不能靠猜，要靠探测和对账：去邮箱的已发送列表里查、去订单系统里查、去支付流水里查。查到了，转 `CONFIRMED`；查不到或有歧义，转人工。账本不装全知，但保证每个悬案都有下文。

**第四，用幂等键和租约 fencing 挡住重复。** 同一个幂等键的第二次登记会被识别；并发场景下租约 fencing 保证只有一个持有者能推进，过期的副本会被拦下。

这套机制里最难的不是账本本身，是「外部真值」这四个字。不是每个副作用都有地方可查：发邮件可以查已发送列表，扣款可以查支付流水，但有些工具调用天生没有回执。所以账本对这类效果只承诺两件事——把不确定性显式记下来，把转人工的路修平。一个承认自己不知道的账本，比一个什么都敢答的系统可信得多，这是我们从内部事故复盘里带出来的教训。

一句话概括：**不抢你的编排，只治理你的副作用。** agent 框架照用，编排逻辑照写，账本在旁边记账、对账、拦重复。

## 三

这个思路今天以 **HongYun 超级運維智能體（HongYun SuperOps）** 的名字开源，三个组件：

**effect-ledger（效果账本）** ——上面说的全部机制的载体：副作用登记、幂等键、租约 fencing、`UNCERTAIN` 对账转人工、审计事件。SQLite 起步，零外部依赖，pip 装上就用。

**modelhub（模型接入管理）** ——副作用要记账，模型接入同样要治理。本地和云端 provider 统一注册，健康探活必须走真实推理实测（自报绿灯不算绿，这是我们内部踩过坑之后立的铁律），本地优先路由带回退链，密钥只存引用、永不入库明文，外加 token 用量统计。

**ops-console（运维控制台）** ——账本的可视化：效果账本浏览、DAG 视图、鉴权。有一条写进代码的红线：控制台只读加白名单命令，绝不做第二个调度器。运维工具最大的腐败就是顺手变成控制系统，我们提前把路堵死。

这三件东西不是在真空中写出来的。它们从我们内部一支长期运行的 agent 舰队的生产代码里抽取而来：747 个测试用例、一批专门用来打脸的反例夹具、崩溃恢复的端到端场景验证，以及影子执法模式的量化结果——误拦率实测 0.00%。也就是说，在真正接管拦截之前，我们先让这套逻辑在旁边静默运行了一段时间，统计它「如果出手会拦错多少次」。结果是零。

设计上，SuperOps 承袭了 HongYun 一条更深的脉络：受东方哲学启发的仿生进化机制。这句话在这里点到为止，展开是另一篇文章的事。

## 四

为什么现在开源，而且开得更彻底：`effect-ledger` 和 `modelhub` 核心全部 Apache-2.0，没有 open-core 剪刀差。商业版（多租户控制台、合规审计报告）在计划里，但还没上线——我们不想在 README 里写一个不存在的预约通道。

我们相信重复副作用这个问题只会越来越贵：agent 的权限在变大，从读网页走向动钱包。每一个把 agent 推向生产的团队，迟早要回答「它到底执行过没有」这个问题。与其到时候临时补，不如现在就把账本立起来，也顺便把你们踩过的坑告诉我们。

包正在从生产代码里做最后的解耦，即将发布到 PyPI。想提前拿到构建、想聊你的场景怎么接、或者单纯想吵一架「这问题根本不该这么解」：
